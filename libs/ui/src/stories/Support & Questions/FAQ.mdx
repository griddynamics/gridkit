# 💬 FAQ

## Q: How do I avoid conflicts when migrating to a UI library(MUI) that also relies on Emotion’s ThemeProvider?

Emotion’s ThemeProvider provides a single theme object for all consumers. Starting in v0.4.0, we corrected the theme argument in styled components. Because we use the same provider as MUI, MUI now reads from our theme and expects its own fields. If those fields are missing, conflicts occur. For future changes, either:

- Add the required MUI keys to our theme (as shown in the example), or
- Merge our custom tokens into an MUI theme to keep a single, compatible theme shape.

```tsx
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import { ThemeProvider as GdThemeProvider } from 'gd-design-library';
import { createTheme, ThemeProvider as MuiThemeProvider } from '@mui/material/styles';

import App from './App';

const muiTheme = createTheme({});

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <GdThemeProvider isDefault>
      <MuiThemeProvider theme={muiTheme}>
        <App />
      </MuiThemeProvider>
    </GdThemeProvider>
  </StrictMode>
);
```

The issue appears to be on MUI’s side. The failure occurs because MUI does not isolate its theme usage when sharing Emotion’s ThemeProvider. When a page includes both MUI and another library that uses @emotion/react, they share the same provider, and MUI attempts to consume our library’s theme, which leads to conflicts.
